# DukenAI Scales

Electron-приложение для подготовки и загрузки товаров в весы Rongta RLS1100.
Каркас и страница входа перенесены из `pos-system-client`.

При запуске приложение автоматически выполняет диагностику ПК и подключения.
Она работает без интернета и авторизации. В отдельном разделе Maria доступны
вход, восстановление сессии, отображение учётной записи и выход.
Выбор организации/магазина, локальная БД и загрузка каталога из Maria
будут добавлены отдельно. Для аппаратной проверки есть ручная передача одного
тестового товара и фиксация результата печати.

## Первый запуск на Windows

1. Откройте GitHub Actions → Build для нужного коммита. Скачайте артефакт
   `scales-windows-<commit>`, распакуйте ZIP и установите `dukenai-scales-setup.exe`.
   Установщик можно перенести с Mac на ПК флешкой; отдельный Node.js не нужен.
2. Запустите приложение. Локальные проверки выполняются автоматически один раз
   за запуск. Отсутствие интернета или настройки Maria их не блокирует.
3. Сохраните текущие настройки Ethernet ПК и подключите весы напрямую кабелем.
   Посмотрите фактический IP и маску в меню весов. Назначьте ПК другой адрес
   той же подсети; для прямого подключения шлюз и DNS не требуются.
4. Введите IP весов, выберите проводной адаптер и нажмите «Сохранить и проверить».
   Порт 5001 — значение из исследованной программы, а не подтверждённая настройка
   конкретных весов. Приложение само не меняет сетевые настройки Windows.
5. Нажмите «Сохранить отчёт», выберите папку и перенесите созданную подпапку
   с `report.json` и `report.txt` на Mac для анализа.
6. После теста верните прежние настройки Ethernet, включая DHCP, если он был включён.

При следующих запусках профиль используется автоматически. «Повторить» создаёт
новый отчёт, «Остановить» сохраняет частичные результаты. Каждый запуск имеет
отдельный каталог внутри системной папки логов приложения; путь виден на экране.
Ошибка записи отчёта отображается явно, и доступен экспорт в другую папку.

Проверяются версии окружения, IPv4-интерфейсы, системные настройки сети, ICMP,
локальный UDP и известный PLU-образец. В отчёте остаются команды и аргументы,
stdout/stderr, коды завершения, время, таймауты, отмена и исходные байты вывода
в base64. Отчёты содержат локальные сетевые адреса и имена адаптеров.

**Автоматическая диагностика не загружает товары.**
Ping проверяет доступность IP через системный маршрут, локальный UDP-тест —
работу сокетов ПК, а PLU-тест — формат исследованного образца. Это не подтверждает
совместимость прошивки, запись товара или печать.

## Тест передачи и печати

1. Сохраните профиль весов и дождитесь завершения диагностики. В карточке передачи
   проверьте адрес назначения и число десятичных разрядов цены на весах — 2 или 3.
2. Нажмите «Передать TEST APPLE». Передаётся один тестовый товар:
   `LFCode 900001`, `Code 0000900001`, цена `12.34` за кг. Товар с этим LFCode
   может быть перезаписан. Используйте тестовые весы или предварительную резервную
   копию каталога; сохранность остальных PLU на конкретной прошивке ещё не проверена.
3. Приложение открывает сеанс, проверяет поддерживаемый ответ возможностей,
   отправляет пакет штатного обновления PLU и завершает сеанс. При неизвестной
   структуре ответа запись не выполняется. Полная загрузка каталога, очистка,
   настройка этикетки и обновление прошивки не вызываются. Как в исследованной
   программе, открытие сеанса содержит текущие локальные дату и время ПК.
4. После подтверждения передачи проверьте печать на клавиатуре весов:
   обнулите пустую платформу, выключите AUTO для одной ручной этикетки,
   положите груз и дождитесь стабильного веса. Коротко нажмите
   `PLU → 900001 → PLU`, проверьте `TEST APPLE` и `12.34` за кг, затем нажмите
   `PRN/ENTER`. Долгое нажатие PLU открывает редактирование.
5. В приложении запишите результат печати и замечания: фактические название,
   цена за кг, вес, сумма и строка со сканера. Сохраните отчёт и фото этикетки.

Команда удалённой печати для этого протокола не подтверждена. Приложение не
имитирует нажатие PRN/ENTER: результат печати фиксируется со слов оператора.
Последовательность клавиш описана в [руководстве Rongta, раздел 5.2](https://fr.rongtatech.com/uploadfile/downloads/RLS%20Series%20User%20manual_V1.3_EN.pdf#page=12).

Тест использует экспериментальную реализацию, восстановленную из RLS1000 v1.129.
ACK означает подтверждение пакета, а не проверку содержимого каталога, суммы
или штрихкода. Отправленные и полученные байты, адреса, стадии, таймауты и отмена
сохраняются в отчёте. При потере ответа товар **мог быть записан**; автоматического
повтора записи нет. Сначала проверьте товар на весах. Кнопка «Повторить» запускает
только обычную диагностику; для следующей записи нужна отдельная кнопка передачи.

## Запуск

Используйте Node.js 22 и npm:

```sh
nvm use
npm ci
cp .env.example .env
npm run dev
```

В `.env` задайте `VITE_API_URL` — корневой URL API без `/v1`, например
`http://localhost:4004`. Это публичная настройка сборки, не место для секретов.
После изменения адреса перезапустите dev-сервер или пересоберите приложение.
Для авторизации в разделе Maria нужен доступный бэкенд и существующая учётная
запись. Экран диагностики доступен и без `VITE_API_URL`.

Если Electron установлен неполностью, проверьте `node --version`, переключитесь
на Node.js 22 через `nvm use` и повторите `npm ci`.

## Авторизация

Приложение использует существующие `/v1/auth/login`, `/v1/auth/refresh`,
`/v1/auth/logout` и `/v1/users/me`. В login передаётся `client_type: "web"`,
чтобы не зависеть от кассовых смен. Пароль не сохраняется. Access token хранится
в `sessionStorage` под ключом `scales.access-token`, refresh token — в HttpOnly
cookie, которой управляет сервер. Logout очищает состояние после успешного
ответа сервера; ошибка сети оставляет возможность повторить выход.

Production renderer загружается с origin `maria://app`, как в POS. Для входа
сервер должен разрешать этот origin и фактический dev-origin (адрес из вывода
`npm run dev`) в `CORS_ORIGINS` с credentials. Production API использует HTTPS
и совместимые cross-origin refresh-cookie (`SameSite=None; Secure`).
Настройки cookie локального backend-окружения отличаются, поэтому восстановление
входа отдельно проверяется с production-сборкой и целевым API.

При открытии раздела Maria приложение проверяет refresh-cookie. Если сервер недоступен, оно
показывает ошибку с повторной попыткой. Вход без сети и автономный доступ к
каталогу в этот этап не входят.

## Проверки и сборка

```sh
npm test
npm run lint
npm run typecheck
npm run format:check
npm run build
npm start
```

`npm run build` создаёт `out/`. `npm start` открывает собранное приложение.
`npm run build:win` на Windows создаёт NSIS-установщик x64 в `dist/`.
Workflow Build выполняет проверки и сборку установщика на Windows, сохраняет
установщик в артефактах запуска на 14 дней.
Отдельный workflow Lint проверяет ESLint и форматирование на Ubuntu.
Оба запускаются для PR в `main` или вручную. Dependabot ежемесячно проверяет
обновления npm-зависимостей. Конфигурации и шаблон PR взяты из `pos-system-client`.

## Релизы Windows

Workflow Release Windows собирает и загружает установщик при публикации
GitHub Release. В **Settings → Secrets and variables → Actions → Variables**
задайте `SCALES_API_URL` — корневой HTTPS URL production API без `/v1`.

Создайте релиз из `main` с тегом `vMAJOR.MINOR.PATCH`, например `v0.1.0`, и
опубликуйте его. Workflow возьмёт версию из тега, выполнит проверки и вызовет
`npm run release:win`. Версию в `package.json` перед релизом менять не нужно.
Для загрузки используется встроенный GitHub token с правом `contents: write`.

Постоянный адрес последнего установщика:

```text
https://github.com/maria-dev-team/scales-system-client/releases/latest/download/dukenai-scales-setup.exe
```

Для приватного репозитория скачивание требует авторизации GitHub.
Подпись установщика и автообновление внутри приложения пока не настроены.

Архитектура описана в [ARCHITECTURE.md](./ARCHITECTURE.md).

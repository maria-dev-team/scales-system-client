# Архитектура DukenAI Scales

Основа взята из `pos-system-client`: Electron main/preload, React renderer,
общие TypeScript-контракты и feature-based организация интерфейса.

```text
src/
  main/                 # lifecycle окна, renderer protocol и диагностика
  preload/              # узкий типизированный API диагностики
  shared/               # контракты диагностики и конфигурация API
  renderer/
    index.html
    src/
      main.tsx          # автономный старт
      desktop-app.tsx   # диагностика и ленивое открытие раздела Maria
      bootstrap.tsx     # auth provider и QueryClient для Maria
      App.tsx           # выбор состояния авторизации
      common/
        api/            # HTTP, auth/refresh, контракты запросов и ответов
        components/     # общие компоненты и UI-примитивы
        constants/
        helpers/
        lib/
        styles/
      features/auth/    # вход, состояние сессии и экран учётной записи
      features/diagnostics/ # профиль подключения и результаты проверок
```

## Границы процессов

Main владеет окном, системными API и lifecycle. Production использует
`maria://app`, protocol handler обслуживает только файлы renderer и запрещает
выход за его каталог. В renderer включены `contextIsolation` и `sandbox`,
отключён `nodeIntegration`. Произвольные переходы в production, новые окна и
разрешения заблокированы.

Preload предоставляет `window.diagnostics`: получение состояния, сохранение
профиля с запуском проверки, повтор, отмена и экспорт. Main проверяет отправителя
IPC и параметры подключения. Универсального доступа к командам или путям нет.
Сеть весов и локальные файлы принадлежат main, не renderer.

## Автодиагностика

Один экземпляр сервиса в main запускает проверки после готовности Electron.
Повторное создание окна и React StrictMode не создают новый запуск. Renderer
опрашивает снимок состояния, поэтому не теряет завершённые до открытия окна шаги.
Раздел диагностики не импортирует auth transport: серверная конфигурация и
восстановление сессии нужны только при открытии Maria.

Профиль и локальный тестовый товар хранятся в `userData/diagnostics.json`.
Каждый запуск создаёт отдельный каталог в `logs/diagnostics`, после каждого шага
атомарно заменяются `report.json` и `report.txt`. JSON сохраняет исходные байты
stdout/stderr и структурированные результаты. При отмене завершается активная
команда или сокет, сохраняется частичный отчёт. Ошибки сохранения видны в UI.

Системные команды фиксированы и запускаются без shell. UDP-пакеты отправляются
только на loopback; выбранный сетевой адрес проверяется локальным bind.
ICMP через ОС проверяет IP, не протокол весов. Совместимость RLS1100 всегда
отмечена как непроверенная до отдельного аппаратного этапа.

## Renderer

Views отображают состояние, отправляют пользовательские действия и используют
общий API layer. HTTP выполняется в `common/api/requests`, а не внутри JSX.
Ответы backend остаются `snake_case`; внутренние payload-типы — `camelCase`.
Общая сериализация преобразует payload при отправке.

Фичи экспортируют внешний API через корневой `index.ts`. Внутри фичи допустимы
относительные импорты; между слоями используется `@renderer/*` или публичный
API фичи. `common` не зависит от `features`; composition root находится в App.
Новые папки и абстракции создаются только при появлении сценария.

## Сессия

Zustand хранит access token и состояние восстановления, QueryClient — серверные
данные. Auth transport перенесён из POS с защитой от устаревших ответов:
операции с cookie выполняются последовательно, параллельные запросы разделяют
один refresh, данные предыдущего входа не попадают в новый контекст.
Сетевой сбой не означает отозванную сессию. При подтверждённом 401 локальный
доступ сбрасывается; при сетевой ошибке доступна повторная попытка.

После входа показывается минимальный экран учётной записи. Авторизация клиента
весов использует `client_type: "web"`; кассы, смены и продажи сюда не перенесены.

## Проверка изменений

Тестируются авторизация, обновление токенов, конкурентные запросы, валидация
формы, пользовательский сценарий входа/выхода и protocol path traversal.
Перед завершением изменений запускаются `npm test`, `npm run lint`,
`npm run typecheck`, `npm run format:check` и `npm run build`.
Работу настоящих refresh-cookie и CORS нужно проверять с целевым сервером;
тесты HTTP adapter этого не подтверждают.

# Архитектура DukenAI Scales

Основа взята из `pos-system-client`: Electron main/preload, React renderer,
общие TypeScript-контракты и feature-based организация интерфейса.

```text
src/
  main/                 # lifecycle окна, renderer protocol и IPC
    catalog/            # SQLite, синхронизация, доступ и worker
    scales/             # кодирование товаров, загрузка и очистка весов
  preload/              # типизированный API каталога и управления окном
  shared/               # контракты каталога, сети и конфигурация API
  renderer/
    index.html
    src/
      main.tsx          # старт оболочки приложения
      desktop-app.tsx   # статус-бар, уведомления и ленивый запуск Maria
      bootstrap.tsx     # auth provider и QueryClient для Maria
      App.tsx           # выбор состояния авторизации
      common/
        api/            # HTTP, auth/refresh, контракты запросов и ответов
        components/     # общие компоненты и UI-примитивы
        constants/
        helpers/
        lib/
        styles/
      features/auth/    # вход, сессия, выбор организации и магазина
      features/catalog/ # рабочее место, каталог и настройки весов
      features/status-bar/ # контекст, сервер, часы и управление окном
```

## Границы процессов

Main владеет окном, системными API и lifecycle. Production использует
`maria://app`, protocol handler обслуживает только файлы renderer и запрещает
выход за его каталог. В renderer включены `contextIsolation` и `sandbox`,
отключён `nodeIntegration`. Произвольные переходы в production, новые окна и
разрешения заблокированы.

Preload предоставляет `window.catalog`: запросы состояния и операций, подписку
на изменения и запрос обновления сессии. `window.windowControls` позволяет
свернуть окно. Main проверяет источник IPC и валидирует команды и параметры;
renderer не может передать произвольный пакет, SQL или путь к файлу.

`CatalogService` управляет отдельным worker и экспортом отчётов. Worker владеет
SQLite, запросами каталога Maria и UDP-обменом с весами. Загрузка и очистка
взаимоисключающие; ошибка worker показывается через состояние каталога.

## Локальный каталог и синхронизация

SQLite хранится в `userData/catalog/catalog.sqlite`. Данные разделены по API,
пользователю, членству, организации и магазину. Токены и пароли в SQLite не
попадают. Настройки устройства и история операций сохраняются при перезапуске.

Начальная синхронизация получает snapshot весовых товаров `unit=kg`, страницы
и последующие изменения от исходного курсора. Новая копия становится видимой
атомарно после завершения; неполная загрузка сохраняет предыдущую копию.
Обновление запускается вручную и раз в минуту. Смена контекста отменяет операции
старого контекста; запросы используют проверенную сервером область доступа.

После онлайн-проверки сохраняется разрешение на восемь часов, защищённое
Electron safeStorage. Оно разрешает локальную работу после потери сети или
перезапуска. Выход, подтверждённый отзыв доступа и истечение срока закрывают
доступ; при недоступном защищённом хранилище перезапуск офлайн не разрешается.

## Обмен с весами

Перед загрузкой проверяются актуальность предпросмотра, PLU, магазинная цена,
единица kg, длина имени и кодировка ASCII/Windows-1251. Префикс поступает из
настроек организации Maria. Сценарий обмена: connect → capabilities → PLU update
для каждого товара → disconnect. Сокет привязан к выбранному локальному адресу;
ответы проверяются по адресу, порту и формату. Чтение возможностей допускает
известный `LB1.00` с именами 36 байт: аппаратный ответ 259 байт без checksum или
261 байт с проверкой checksum. Исходящие пакеты содержат 261 байт.

Точный набор товаров и пакетов сохраняется перед отправкой. При таймауте нет
автоматического повтора: товар мог быть записан. Подтверждения ACK и исходные
байты обмена сохраняются в истории, доступной для экспорта в JSON/TXT. Ошибка
сохранения останавливает дальнейшие отправки. После аварийного закрытия
незавершённые операции помечаются прерванными, а отправленные без подтверждения
товары — с неизвестным результатом; операции автоматически не возобновляются.

Очистка всех PLU требует отдельного одноразового подтверждения сохранённого
адреса и поддерживается для `LB1.00 / LS`. Отправляются только две проверенные
команды очистки диапазонов товаров; каталог Maria, локальные товары и макеты
этикеток остаются. Подтверждённая очистка сбрасывает учёт ранее отправленных
товаров этого устройства, сохраняя историю операций.

ACK подтверждает пакет, но не чтение данных обратно или правильность этикетки.
Печать проверяется оператором на весах; макет загружается через официальный
RLS/RTLabel. Страница диагностики и её фоновый сервис удалены. Общие сетевые и
протокольные функции, оставшиеся в `main/diagnostics`, используются каталогом
или его автономными тестами; системные диагностические команды при старте
приложения не запускаются.

## Renderer

Views отображают состояние, отправляют пользовательские действия и используют
общий API layer. HTTP выполняется в `common/api/requests`, а не внутри JSX.
Ответы backend остаются `snake_case`; внутренние payload-типы — `camelCase`.
Общая сериализация преобразует payload при отправке.

Фичи экспортируют внешний API через корневой `index.ts`. Внутри фичи допустимы
относительные импорты; между слоями используется `@renderer/*` или публичный
API фичи. `common` не зависит от `features`; composition root находится в App.
Новые папки и абстракции создаются только при появлении сценария.

## Сессия

Zustand хранит access token и состояние восстановления, QueryClient — серверные
данные. Auth transport перенесён из POS с защитой от устаревших ответов:
операции с cookie выполняются последовательно, параллельные запросы разделяют
один refresh, данные предыдущего входа не попадают в новый контекст.
Сетевой сбой не означает отозванную сессию. При подтверждённом 401 локальный
доступ сбрасывается; при сетевой ошибке доступна повторная попытка.

После входа пользователь выбирает организацию и магазин и открывает рабочее
место с каталогом и настройками весов. Авторизация клиента весов использует `client_type: "web"`; кассы, смены и продажи сюда не перенесены.

## Проверка изменений

Тестируются авторизация, обновление токенов, конкурентные запросы, валидация
формы, выбор контекста, вход/выход, protocol path traversal, синхронизация,
восстановление SQLite и обмен с локальным UDP-эмулятором весов.
Перед завершением изменений запускаются `npm test`, `npm run lint`,
`npm run typecheck`, `npm run format:check`, `npm run build` и
`npm run smoke:catalog`. Последняя команда проверяет собранный worker в Node.js
из Electron с отдельной временной SQLite-базой.
Работу настоящих refresh-cookie и CORS нужно проверять с целевым сервером;
тесты HTTP adapter этого не подтверждают.
